# Autonova CRM — Implementation Review

_Review date: 8 November 2026. Reviewed branch `main`, HEAD `9f26972db04d75fd5010167ee38c449cd80bc7d7`, plus the complete pre-existing working tree. This is a static repository review; no source code, configuration, database, or existing audit files were changed during evidence collection._

## Executive summary

The repository contains useful identity/security foundations and one persisted lead CRUD slice. It does **not** contain the sales pipeline described by the PRD, nor any of modules 4.2–4.10 beyond design documentation. The current lead record has a single `stage` string, but there is no constrained stage domain, deal aggregate, transition workflow, lost/disqualified outcomes, history of stage changes, dashboard, or reporting. The lead creation default of `NEW_LEAD` is not proof that the lifecycle is implemented.

The mandatory commercial invariant is not executable: no ToR, version, signature, quotation, Won transition, client account, or conversion operation exists. Quote acceptance and one/both party signatures therefore cannot be distinguished by the application. Revisit-later auto-return and Lost reason retention are absent. Do not use this system as the operational sales source of truth or claim production readiness.

Identity/access is substantially more advanced than the older roadmap snapshot suggests: the working tree has MFA, invitation acceptance/email, permission checks and lead ownership scoping, with a sprint record of passing tests. Director MFA remains a hard product-use prerequisite and production recovery/operations remain unverified. The production gate is further limited by absent staging/deployment, backups/restore evidence, and the absence of all downstream CRM modules.

The original SOW file and its pipeline diagram are not present in the repository or supplied attachment; only the PRD's transcription/expansion is available. Thus the comparison below uses PRD requirements and records SOW verification as blocked by source availability. The requested `clear-error-handling-clean-architecture` skill was not found in the skill directories available to this workspace. Architecture checks below follow the brief's criteria and `docs/02-architecture.md` / `docs/08-development-conventions.md`.

## Sales pipeline review

### Exactly one current stage

**Finding: not guaranteed as a valid business stage.** `Lead.stage` is one scalar field (`apps/api/prisma/schema.prisma:78-107`) so a row cannot hold two separate stage values at once. However it is a free-form `String`, not a Prisma/database enum or constrained domain. The database migration defaults it to `NEW_LEAD` but does not add a stage check constraint (`apps/api/prisma/migrations/20261107160000_leads/migration.sql`). The API currently prevents clients from changing stage by rejecting unknown PATCH fields (`leads.schemas.ts:32-53`), and create initializes it through the DB default. There are no transition operations at all. Therefore:

- It is not correct to say each **deal** has exactly one stage: there is no Deal model, only a Lead row with a stage string.
- It is accurate that the current record schema stores one stage value per lead, but it does not constrain that value to one of the approved pipeline states. Direct DB writes or future defective code can produce an unrecognized stage.
- There is no valid-transition validation, optimistic version, row lock, transition audit, or transaction behavior to review for concurrent stage changes because stage changes are not implemented.
- The lead list labels whatever string it receives; there is no pipeline-stage aggregation/dashboard query. A value outside recognized labels can become unclassified or disappear from meaningful pipeline reporting; no reporting currently exists.
- Disqualified, Lost and Won are not modeled. A single string alone would not define their reasons, dates, terminal rules or relationships to signatures/conversion.

The implementation therefore does not meet the SOW sentence that every deal sits in exactly one stage. The desired durable correction is a product-approved explicit lifecycle (including whether Disqualified is a stage or outcome), a constrained stage value and a transactional transition use case that writes history and protects terminal invariants.

### Revisit-later

**Finding: absent.** The current `nextActionAt` field is a generic reminder (`schema.prisma:95-96`), not a disqualification follow-up. There is no disqualification reason or revisit date field, no qualification route/model, and no worker/scheduler package or cron integration. No automatic re-entry exists. The API and web UI can create/edit ordinary next actions, but neither changes a disqualified lead to New Lead on a scheduled date. The app being offline, delayed/double job execution, idempotency, Nairobi date boundaries, audit of re-entry, and repeated scheduling are consequently not handled. A displayed overdue date would not meet the requirement.

### Lost deals

**Finding: absent.** No Lost state, lost reason field, transition endpoint, audit action, or reporting query exists. The basic lead update API cannot alter stage and has no reason to persist. No frontend or backend Lost workflow exists. Lost cannot be reliably grouped for reporting, and there is no Won conversion path against which to enforce mutually exclusive outcomes.

### Won, ToR and client conversion

**Finding: absent and a critical business risk.** Searches of the API/web modules and Prisma schema show no ToR/version/signature, quotation, client account, or conversion models/routes/screens. No dual-party signature verification can require signatures on the same final immutable ToR version. No transaction can atomically record the final signature, mark Won, create a unique client account, attach the signed version, or prevent duplicate conversion. The pipeline's central commercial invariant is documented in PRD and flow docs but unenforced in code. No claim of electronic-signature compliance is supported.

## Cross-cutting architecture and engineering review

### Backend and data

- **Layering:** Auth and leads separate presentation, application/use cases, and repository/infrastructure. The controller delegates to `LeadsUseCases`, and persistence sits in `LeadsRepository`. This matches the modular-monolith conventions for a simple CRUD slice. There is no business domain layer yet; that is reasonable for CRUD but insufficient once lifecycle/qualification/ToR rules are introduced (`docs/02-architecture.md`, `docs/08-development-conventions.md`).
- **Validation and errors:** Lead request bodies use strict Zod schemas and shared validation pipes; the API has an exception filter/error envelope and request IDs. This is a sound foundation. Cross-field update validation has a possible edge case: changing an existing lead's source to `REFERRAL` requires referrer in that same patch, while changing away from referral does not clear a stored referrer. Confirm desired behavior in a complete update model. No unsupported runtime test was performed here.
- **Authorization:** Every lead endpoint declares a permission; service/repository scope BD reads/writes to owner and permits Director-wide access. E2E source asserts access boundaries. There is no reassignment operation. UI permission checks are not relied on as the security boundary. Confirm remaining role/visibility requirements before feature grants.
- **Transactions/audit:** Lead create/update and audit inserts share a Prisma transaction (`leads.use-cases.ts:41-55,68-80`). Snapshots record selected fields/change flags. No stage history exists because transitions do not exist. Optimistic concurrency is not present on lead edits, despite the database design doc proposing version columns when aggregates are added (`docs/04-database-design.md`).
- **Database integrity:** Unique email for users and FKs/checks around identity/audit are present; lead source is a DB enum. Lead `stage` and `currency` are free-form strings, `productInterest` free text, and company/contacts are unnormalized. No lead duplicate constraint or pipeline-stage check exists. Use decimal strings/Prisma Decimal for estimate values, but there is no full commercial calculation to assess.
- **Idempotency/jobs:** No business job/queue/worker exists. No idempotency key or conversion lock exists. Lead create may create duplicates by design because duplicate detection is absent.

### Frontend

- Lead forms use React Hook Form + Zod; remote data is in TanStack Query; auth session state uses React context. This is consistent with the requested division. The form uses local `useState` for a local error message, which is appropriate. No evidence of a CRM-wide Zustand store is needed at this stage.
- Lead screens show loading/error/success and empty states; server field errors map to fields. Stage and product-specific business rules do not exist in the UI because there are no workflow endpoints. UI-only visibility checks do not substitute for API authorization.
- The next-action `date` input converts the local date at 09:00 before `.toISOString()` (`apps/web/src/features/leads/lead-form.tsx:126-143`), while storage is `timestamptz`. This is a pragmatic reminder-time choice but not a date-only business model; future date-boundary jobs must explicitly use `Africa/Nairobi` and define date-only semantics to avoid UTC/Nairobi boundary errors.
- No dashboard, activity history, ToR, billing, support or notifications UI exists. No device-based acceptance evidence proves the under-two-minute mobile capture criterion.

### Authentication, security and operations

- Code/tests/docs show Argon2id, short-lived HS256 access tokens, DB-backed sessions checked per request, opaque hashed refresh token rotation/replay revocation, origin/CSRF checks, restricted Director sessions until TOTP verification, encrypted TOTP secrets, one-time recovery codes, deny-by-default permission guard, invitation activation and lead ownership scoping. Relevant files include `apps/api/src/modules/auth/`, `apps/api/src/modules/users/`, `apps/api/src/common/`, `apps/web/src/features/auth/`, `docs/06-security-and-access-control.md`.
- MFA is implemented for Director access, but no Director-to-Director reset flow or key rotation procedure is evidenced. Invitation SMTP exists via Nodemailer/Mailpit for local use; production SMTP provider and sender are unresolved. Password reset is absent.
- Audit log has DB protections as documented in schema/migrations and the existing API tests, but no business events exist for the missing workflows. Audit does not replace domain history tables for scope rounds/signatures/stage transitions.
- No production deployment/CI, TLS/proxy, monitoring, backup schedule, encrypted backup, restore drill, retention/recovery objectives, or production environment evidence was established. Local Compose and health checks do not establish production readiness.
- File-upload, privacy-sensitive GPS/voice/photo, ToR signer identity, and finance data controls are future requirements; no upload exists to assess for size/type/scanning/access policy.
