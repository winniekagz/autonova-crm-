## Priority summary

P0 gaps stop the core sales lifecycle or leave high-impact control/data-integrity rules unenforced. P1 gaps prevent the minimum modules 1–6 go-live outcome stated in the task/SOW brief. P2 items complete later client operations. P3 items improve the service after core workflows exist. “Decision required” identifies policy that engineering must not infer.

## Dependency-aware implementation sequence

This sequence completes end-to-end workflows. The file paths are likely touchpoints, not a promise that all code belongs in one file. Each step needs its own reviewed migrations and feature tests; do not run destructive E2E setup against any non-test database.

- **Scope:** Get canonical SOW; record stage/outcome state machine and go-live boundary; settle date-only/Nairobi behavior; approve roles/visibility, BANT, Lost reasons, ToR signature/version and financial rules.
- **Likely files:** `docs/prd.md`, `docs/flows/lead-management.md`, `qualification.md`, `terms-of-reference.md`, `quotations.md`, `client-conversion.md`, `docs/decisions/`.
- **Dependencies:** Stakeholder availability.

### 1. Implement constrained lead lifecycle, reasons, and reliable revisit re-entry

- **Priority:** P0; first implementation after Step 0.
- **Scope:** Replace string-only stage with approved constrained state; add transition history and reason/date fields; define idempotent due-date job. Keep Won impossible until signature workflow exists; never add a manual “mark Won” bypass.
- **Likely backend:** `apps/api/prisma/schema.prisma`, new migration, `apps/api/src/modules/leads/{domain,application,infrastructure,presentation}`, `apps/api/src/modules/audit/`, `apps/api/src/app.module.ts`; add a worker/scheduler only when the first job exists, consistent with `docs/03-implementation-roadmap.md` and ADR-001.
- **Likely frontend:** `apps/web/src/features/leads/`, lead detail/list and stage/qualification forms; show transition history and reasons.
- **Database:** stage enum/check, lead version/transition history, disqualification reason, date-only revisit value, pending schedule/outbox key and indexes. Backfill current `NEW_LEAD`; fail migration if other values require human resolution.
- **Dependencies:** Step 0 stage rules/timezone; job execution model and operational owner.
- **Acceptance criteria:** one canonical current stage per lead; invalid stages/transitions rejected by API and DB; Lost requires reason and cannot be lost in later edits; revisit requires date; due leads re-enter New Lead once on/after Nairobi follow-up date, including after downtime; previous disqualification and all attempts remain auditable; stale/double job execution causes no duplicate transition; won transition requires verified signature gate and stays unavailable pending Step 5.
- **Tests:** API/domain transition matrix; migration constraint; concurrency conflict; missing/late/double/rescheduled/cancelled due job; Nairobi date-boundary/fixed clock; audit transaction rollback; integration test that all active/terminal states appear once in pipeline aggregation.
- **Documentation:** state diagram, API reference, audit and job runbook; mark stage transitions implemented only after tests pass.
- **Risk/decision:** Do not guess the business timezone or whether manual reopen is permitted.

**Concrete revisit job design:** store a date-only `follow_up_on` and a pending scheduled event keyed by lead + schedule generation. A durable server-side worker repeatedly selects pending records where `follow_up_on <= current_date_in_Africa/Nairobi`, claims them with a conditional update/row lock, then in one transaction verifies lead is still in revisit-pending state and schedule generation matches, records a `lead.revisit_due`/`lead.stage_changed` history event and audit row, changes stage to New Lead, and marks the schedule complete. A unique key plus conditional state update makes reruns idempotent. A catch-up query handles the app being offline; no dependency on browser timers or an in-memory cron occurrence. Rescheduling increments generation and supersedes stale jobs. If a lead was manually changed/closed, the conditional stage check leaves it unchanged and records a skipped/cancelled outcome. All date comparisons use one injected Nairobi business clock/date helper; test exact midnight and the day before/after. Alert on repeatedly failing jobs and retain retry/error state.
